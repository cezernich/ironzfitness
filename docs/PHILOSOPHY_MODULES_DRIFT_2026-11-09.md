# Philosophy modules drift report (2026-11-09)

Read-only analysis. **Nothing in production was changed.** Purpose: decide how to reconcile the `philosophy_modules` table before any sync or retirement (see `sources-of-truth/README.md` section 3).

## Who reads these modules

`js/philosophy-engine.js` (load order: Supabase table → browser cache → `modules_static.json`), the legacy philosophy planner and rules engine, `app.js`, `db.js`, `admin.js`, `seed-reference-data.js`, `coach-sheet-import.js`, and the **`ask-ironz` edge function**. The main race-plan path (`planner.js` `generateTrainingPlan`) does not use them.

`rationale` and `evidence_sources` were not compared.

## What the gaps mean for users

- **Injury modules are missing live.** Onboarding collects injuries and the engine classifies them (`classifyInjury`), but no `INJURY_*` module exists in the table, so users who report an injury get no injury-specific rules from the legacy planner or Ask IronZ.
- **Recovery modules are missing live.** The engine requests `RECOVERY_*` only when recovery state is moderate or low; none exist, so nothing applies. (Missing recovery data defaults to `good`, so these modules would not fire for users without reports.)
- **Two `critical`-priority modules are missing live** (`TRAINING_THRESHOLD_WEEK`, `VOLUME_TIME_SCALING`).
- **Golden tests can't detect any of this**: they pass with both the 47 and 60 sets (verified), and none of the cases include an injury or recovery state.
- `SPORT_PILATES` exists only in production and has no copy in GitHub.

## Options

| | A. Full sync to JSON (60) | B. Freeze table, retire with legacy engine | C. Additive: injury + recovery only (6 modules) |
|---|---|---|---|
| Closes the injury/recovery safety gap | Yes | Not until retirement | **Yes** |
| Blast radius | Large: changes plan_rules on 8 modules for every legacy-plan and Ask IronZ user | None now | **Small**: fires only for users who report an injury or moderate/low recovery |
| Effort | Medium | Low now, high later | **Low** |
| Fits direction (Rule Engine replaces legacy) | Invests in code being retired | Yes | Yes |
| Test needs | Golden cases for every changed module | none now | New golden cases with injury and low recovery |

## Recommendation

**C now, then B.**

1. **Back up first:** export the live table into the repo (`sources-of-truth/philosophy/db_snapshot_2026-11-09.json`, generated by the service-role sync script or a dashboard export), so production can be restored exactly and `SPORT_PILATES` is in GitHub.
2. **Add golden cases** with a reported injury (knee, shoulder, general) and moderate and low recovery. Confirm they fail against the live set and pass with the 6 modules added.
3. **Apply the 6 modules to staging**, run the golden tests and a manual Ask IronZ check, then to production, in a dedicated PR with a rollback script (delete the 6 ids).
4. **Leave the 8 plan_rules differences and the 9 other missing modules alone.** Fold whatever is still right into the master spec / Rule Engine, and retire the table when its consumers move off it (Ask IronZ last).
5. **Decide the 3 static-vs-DB differences** when the snapshot is in hand (which version is correct).

## Reproduce

Live fingerprints (Supabase SQL editor, read-only):

```sql
select id,
  left(md5(coalesce(applies_when::text,'')),8)         aw,
  left(md5(coalesce(principles::text,'')),8)           pr,
  left(md5(coalesce(plan_rules::text,'')),8)           plr,
  left(md5(coalesce(hard_constraints::text,'')),8)     hc,
  left(md5(coalesce(nutrition_rules::text,'')),8)      nr,
  left(md5(coalesce(training_adjustments::text,'')),8) ta,
  left(md5(coalesce(coaching_tone,'')),8)              ct
from public.philosophy_modules order by id;
```

For the files, load each JSON into any Postgres and compute the same values, converting array fields with `array(select jsonb_array_elements_text(doc->'<field>'))::text` so they match the DB's `text[]` format.
